# Paper 恢复与观察

本手册只适用于 Paper，不授权 Testnet、Live、交易所私有接口或真实凭据。生产演练必须先取得当前任务授权，并确认数据库、制品目录和应用镜像属于同一可恢复点。

## 验证基线

开始正式 Paper 观察前，保留 Backend 构建、静态分析、容器健康检查、数据库备份恢复脚本和本手册人工演练记录。不得把未执行或跳过的恢复步骤写成已完成。

## 演练前记录

1. 记录 UTC 时间、环境、发布标签、完整 commit、数据库 migration 版本和镜像 digest。
2. 确认目标工作流只使用 `official.binance.paper_execute`，`liveTradingEnabled` 未开启且环境中没有真实交易密钥。
3. 创建数据库与 Backend `data/backend/artifacts` 制品目录的一致备份，并实际验证恢复命令可读取。
4. 记录目标 Paper 工作流、账户 ID、待处理运行/任务数量，以及各事实表的总数和不同 `operation_key` 数量。证据不得包含原始载荷、Token、DSN 或个人数据。

## 重启与积压

1. 让一个 Paper 运行停在人工等待，并保留至少一个排队运行。
2. 只重启 CoinSphere Backend；不要执行 Compose `down`，不要操作共享服务。
3. 验证等待任务仍为 `pending`、排队运行仍可领取、同分区顺序未改变。
4. 批准或拒绝任务，确认原运行从 Checkpoint 继续，而不是重新产生信号、成交或通知。
5. 对失败运行执行一次白名单重试，对活动运行执行取消，再停用固定工作流；记录预期的 `409` 状态冲突和成功结果。

## 账本一致性检查

当前没有在线账本重建接口，恢复演练不得调用不存在的管理 API 或直接改写投影。重启前后比较：

- 订单、成交、费用和账本行数及操作键完全不变。
- 账户现金等于初始余额加账本金额总和。
- 持仓数量等于成交数量按买卖方向汇总后的净变化。
- 同一 `clientOrderId` 不会对应不同账户、市场、品种、方向、数量或仓位效果。

不一致时立即暂停工作流，保留数据库和日志证据；不得修改事实表、伪造 migration 版本或执行 Down。

## 插件升级

在非生产恢复副本上演练插件升级：旧 migration 字节不变，只追加更高版本；当前定义、在途 Run 或未撤销 ResultView 引用时升级和卸载均拒绝。解除当前引用并完成新版本图处理后才升级，再重新建立定义/视图并检查账本。跨 major 遵循相同前提，不提供自动兼容；generation 3 → 4 使用[独立目标与恢复流程](database-migrations.md)，不迁旧 Paper 事实或观察证据。

## 观察门禁

使用 [Paper 观察证据模板](../templates/paper-observation-evidence.md)记录 CI、发布、恢复、账本和视觉验收链接。只有用户确认这些证据满足要求后才能开始正式 Paper 观察；代码合并、发布和部署本身不构成观察、Testnet 或 Live 放行。
