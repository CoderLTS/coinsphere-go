# ADR-0010：目标仓位执行、硬风控与追加式交易事件

- 状态：接受
- 日期：2026-08-05

## 背景

旧设计使用通用 Realm 权限状态机、复式分录和复杂凭据封装，并以固定观察天数和订单数晋级。自用系统仍需要严格的下单幂等、风控、保护单、恢复和对账，但不需要通用会计平台或为样本数本身维护治理机制。

## 决策

- 策略实例分别记录 `signal_only | manual | auto` 和 `paper | testnet | live`。手动信号在下一根 K 线闭合时过期；自动模式同时要求管理员授权和用户启用。Live auto 另记录独立的 Owner 放行，任何暂停都会撤销 Owner 的 manual/auto 放行，但不能阻断保护单或紧急平仓。
- 同一 `account + market + symbol` 最多一个 manual/auto 策略拥有活动仓位，使用数据库部分唯一约束保护。
- 账户必须显式配置品种白名单、账户总名义金额、单品种金额、单笔金额、日亏损、最大回撤和报价最大年龄；USD-M 另固定低杠杆、逐仓和单向持仓。缺少任一适用上限时禁止自动化。
- 风控或全局急停触发后暂停自动化并阻止增仓，只允许减仓、平仓和撤单。解除急停不能自动恢复策略。
- Go Executor 是唯一交易所私有协议边界。每个意图使用稳定 `intentId` 和确定性 `clientOrderId`；未知状态先查询，禁止无条件重试下单。
- 自动调仓只使用市价差额单。Spot 使用随受管仓位重建的数量型交易所止损；USD-M 使用 `STOP_MARKET + closePosition=true + workingType=MARK_PRICE`，不同时携带 `quantity` 或 `reduceOnly`。
- 保护单无法确认时立即市价平仓、暂停策略并生成关键通知；平仓状态未知时保持禁止增仓并持续对账。
- 本地只追加 `order/fill/fee/funding` 事件；订单、仓位、余额和盈亏是可重建投影。修正追加更正事件，不建设复式账本或通用事件溯源平台。
- 凭据经 HTTPS 提交并复用现有对称主密钥加密，永不回显或记录。V1 不自动验证 Binance 权限，保存前要求用户确认关闭提现和配置 IP 白名单。
- 晋级顺序为 Paper、Testnet、Live manual、Live auto，Spot Live 先于 USD-M Live。晋级依据演练证据、无未解释差异和用户手工放行，不使用固定天数或订单数。

## 结果

- 保留资金安全所需的强约束、幂等恢复和审计事实，同时删除通用账本和过度状态建模。
- 对称主密钥意味着 Go App 与 Executor 的受控部署都需要密钥；通过网络权限、代码边界、日志脱敏和手工部署降低暴露面，不声称实现硬件级密钥隔离。
- Paper、Testnet 和 Live 复用相同意图、事件和投影语义，但每一级仍需独立人工放行。

## 未采用方案

- 通用复式账本：目标只是交易事实对账和仓位/盈亏重建，没有多币种会计报表需求。
- Bot 或工作流直接批准/下单：无法满足登录、复验和风控边界。
- 固定 30 天/100 单：不能替代幂等、恢复、保护单和对账证据。
