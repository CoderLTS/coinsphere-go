# ADR-0002：编译期插件驱动的工作流平台

- 状态：已接受，数据库部署部分由 [ADR-0003](0003-use-shared-postgresql.md) 替代
- 日期：2026-08-24
- 决策所有者：CoinSphere
- 当前实现：[CoinSphere 当前架构](../overview.md)

## 背景

CoinSphere 当前已经具备工作流、调度、事件、策略、回测、通知和 Paper 能力，但用户操作仍围绕工作流定义、节点定义、执行记录、策略、数据、通知和交易等多个后台模块展开。工作流暴露 `entryKey`、原始 JSON、版本和运行入口等实现概念，无法成为用户完成数据采集、策略运行、通知和结果处理的统一工作台。

当前架构还存在两个长期边界问题：

- Python Worker 通过数据库任务协议承担实时策略和回测，实时与回测虽有共同意图，但跨语言契约、部署槽位、制品卷和取消语义增加了系统复杂度。
- 节点是核心代码维护的内置模板。新增量化、连接器、AI 或通知能力需要继续扩大工作流核心，或者引入缺少统一配置、结果和生命周期契约的旁路模块。

本项目按全新系统演进，尚未进入需要保留历史 migration 和正式 Paper 观察证据的阶段。当前允许重置开发数据并建立 SDK v3 基线，因此可以在不增加旧模型兼容层的前提下重新划分边界。

## 决策

### 1. 产品以工作流为唯一配置与运行入口

工作流拥有可视化配置、触发、生命周期、运行观察、历史、重试、取消、重放和人工等待。数据、策略、AI、通知和 Paper 以节点及结果页形式接入。

系统监控仍是首页，工作流是独立一级菜单。首期只有超级管理员可以查看和操作工作流；普通用户只访问由管理员创建并授权的固定范围结果视图，不会看到源工作流。

一个工作流只有一个主触发器，并明确使用批处理、事件响应或连续流模式。工作流本身只有 `inactive / active / error` 生命周期；每次触发创建一个有界 `WorkflowRun`，连续流不保留无限节点调用栈。

### 2. 保持单实例模块化单体和 PostgreSQL 持久运行时

V2 保持 `Vue Web + Go App + PostgreSQL 16`。PostgreSQL 同时保存事件队列、工作流修订、Run、节点尝试、节点日志、检查点、Outbox、人工任务和插件业务事实，不引入 Redis、Kafka、其他消息代理或分布式协调系统。

事件统一采用 CloudEvents 1.0 JSON，投递语义为至少一次；按 `partitionKey` 保序，副作用通过稳定操作键和数据库唯一约束幂等。执行资源只分为普通实时工作的 `stream` 池和回测等重任务的 `compute` 池。

### 3. 使用本地源码、编译期集成的可信插件

插件是开发者或超级管理员从本地目录安装的完整可信源码包。插件可以贡献：

- Action 节点和长运行 Trigger 节点；
- JSON Schema 2020-12、UI Schema 和可选 Vue 配置组件；
- API 路由、独立功能页和结果页；
- PostgreSQL migration；
- 策略等插件专属公共接口实现。

安装命令校验 `coinsphere-plugin.json`，生成 Go 和 Vue 静态注册表，更新依赖及 migration 索引并重建 Compose。应用不在运行时扫描插件目录，不加载共享库，不使用 iframe 或 Web Component 隔离前端，也不启动独立插件宿主。

插件正常通过 SDK 注入的工作流、结果或系统作用域访问数据。由于插件与核心处于同一进程并拥有完整 Go 能力，这些作用域是开发契约而非安全沙箱；只允许安装完全信任的源码，并明确记录插件可以在技术上绕过 SDK 约束。

### 4. 插件契约和版本生命周期由核心统一

节点配置、输入和输出使用 JSON Schema 2020-12，布局使用独立 UI Schema。字段映射保存来源节点和字段数组，不继续使用共享字符串路径。高级转换使用 CEL；金融 Decimal 运算只能在类型化 Go 节点中完成。

SDK 固定提供节点描述符、Action/Trigger 处理器、结果页、作用域路由、密钥读取、命名空间状态和制品访问。官方 Quant、Connector、AI 和 Notification 与外部可信插件使用相同注册、Schema、事件和生命周期契约，不保留核心私有旁路。

插件清单使用 SemVer、`requiresCore` 和 SDK major。minor/patch 升级必须兼容已有节点配置、输入输出和状态。major 升级默认拒绝；受影响工作流由管理员先停用并显式处理，不引入额外生命周期状态。

每个插件拥有独立 PostgreSQL schema 和 migration 序列。卸载存在活动引用时拒绝并列出引用；成功卸载默认保留 schema 和数据，删除数据只能通过单独、显式、破坏性的 `purge-data` 命令。

### 5. 删除 Python Worker，策略统一为可信 Go 插件

V2 删除 Python Worker、realtime/backtest 双槽位任务协议、Worker 服务和制品卷。回测在 Go App 的 `compute` 池执行。

策略是由开发者安装的 Go 插件实现。统一接口接收按时间升序的闭合 K 线、类型化参数和只读上下文，返回 Decimal 目标仓位；策略不保存可变状态、不访问数据库，也不产生通知或交易副作用。实时评估和回测直接调用同一个 `Evaluate` 实现。

系统不提供在线 Go/Python 源码编辑。可信 Go 策略若不响应取消，主进程不能强制终止；只有该限制在实际运行中构成资源或隔离问题时，才引入独立 Go Worker。

### 6. Quant 与交易所插件分离，Live 默认关闭

`official.quant` 只提供通用指标、策略、回测、Signal 和 `OrderIntent`，通过 `MarketDataRegistry` 按 `venue` 读取行情，不包含 Binance URL、代理、签名、行情表或执行账本。

`official.binance` 提供 Spot/USD-M 公共行情、交易规则、Paper 与受门禁保护的市价真实执行。Paper 是默认模式；Live 只有在人工确认、全部风险上限、无提现权限凭据、幂等订单和恢复/对账链路同时满足时才允许，且仍需用户在部署外手工放行。

未来 `official.okx` 只需实现相同的 `MarketDataProvider` 与 `ExecutionProvider`；Core 和 Quant 不增加交易所分支。通用 HTTP、AI 和 Quant 节点不得绕过交易所插件风控或直接调用私有接口。

## 结果

### 正面结果

- 用户围绕工作流完成主要任务，业务页转为结果和必要操作，不再形成第二套配置入口。
- 新能力通过一个可验证契约同时获得节点配置、运行、结果、权限和升级语义，核心不需要了解插件领域细节。
- 实时策略和回测共用 Go 实现，删除跨语言任务协议、第二运行时和额外服务。
- PostgreSQL 继续作为唯一事实源，符合当前自托管规模，不增加消息代理和多进程协调成本。
- 固定修订、检查点、操作键和无副作用诊断重放提供可复现故障证据。

### 负面结果与限制

- 插件安装和升级需要修改构建输入、重建镜像并允许分钟级停机，不能即时启用。
- 完全信任插件没有进程、内存、文件系统或数据库安全隔离；错误插件可以影响整个 Go App。
- Go 策略在主进程执行，忽略取消的实现无法安全强制终止。
- PostgreSQL 队列和单实例调度器不面向高频交易、大规模租户或跨节点容灾。
- 重置 SDK v3 基线会放弃旧开发数据、旧 API 和旧工作流图，不能原地升级现有部署。

这些限制是明确的产品边界，不提前通过插件宿主、消息代理、兼容层或多实例框架解决。

## 备选方案

| 方案                          | 未选择原因                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| 继续扩展内置节点              | 业务能力继续进入核心，无法形成统一的第三方/官方扩展边界，也不能解决分散结果页和生命周期问题     |
| 保留 Python Worker            | 继续维护跨语言任务协议、服务、槽位和取消边界；用户又不需要在线 Python 策略编辑                  |
| Go `plugin` 或动态共享库      | 平台和构建兼容性差，升级与依赖冲突难以诊断，不适合当前 Windows 开发和容器交付                   |
| 独立插件进程或微服务          | 可以隔离不可信代码，但需要 RPC、部署、健康、版本和数据一致性协议；当前只有可信本地插件需求      |
| iframe/Web Component 前端插件 | 会引入第二套路由、主题、权限和通信模型；插件源码已经参与主应用构建，无需运行时隔离              |
| Kafka/Redis/外部队列          | 目标容量为单实例低吞吐，PostgreSQL 已经承担任务、Outbox 和恢复；新增基础设施没有已实现需求      |
| 恢复已回滚的工作台实现        | 旧实现包含有价值概念，但整体信息架构和结果页边界不符合本次需求；V2 只按新契约重新实现需要的部分 |
| 把交易执行继续放在 Quant      | 会让通用策略依赖 Binance 私有协议，接入其他交易所时必须修改 Quant 与 Core                       |

## 数据与兼容策略

P0 在正式 Paper 观察前建立新的核心初始化 migration，并为插件建立独立 schema 与迁移账本。2026-08-28 经用户明确授权，未冻结的 `00005-00009` 开发历史重建为 `00005_workflow_runs.sql`、`00006_quant_market_backtests.sql` 和 `00007_paper_results_notifications.sql`。不编写旧表、旧接口、旧工作流图或 Python 策略的迁移器；需要保留的数据只能在重置前人工导出。

开始记录 Paper 晋级证据前必须冻结核心和插件 migration 历史；冻结后只追加版本。插件卸载不回滚 schema，应用版本回滚也不自动执行 migration Down。

## 安全约束

- 只安装本地、经过代码审查的可信插件；插件清单不提供虚假的沙箱或权限保证。
- 节点密钥独立加密存储，不进入修订、日志、导出、快照或复制操作。
- 普通用户的结果范围只由服务端 ResultView 解析，插件路由不得信任客户端工作流 ID。
- Codex、CI、工作流、AI 和通用 HTTP 节点不得接触真实交易密钥、调用交易所私有接口或发起真实订单。
- Paper 自动模式缺少任一明确风险上限时保持禁用。

## 生效与替代关系

本 ADR 自 P0 开始实现后为 `Accepted`。SDK v3 修订取代 [ADR-0001](0001-workflow-modular-monolith.md) 中的 Python Worker、内置节点限制、在线策略源码以及交易所执行归属决策；ADR-0001 对重构前系统的描述仍保留为历史记录。

如需改回动态插件、独立 Worker、多实例或真实交易，必须新增 ADR，不通过普通实现 PR 隐式改变这些边界。
