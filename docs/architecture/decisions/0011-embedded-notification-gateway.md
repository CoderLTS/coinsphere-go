# ADR-0011：内嵌静态通知网关

- 状态：接受
- 日期：2026-08-05

## 背景

现有 `notify.go` 已实现站内、钉钉、SMTP、加密配置、投递记录、工作流通知节点和 Outbox 集成。为了增加官方 QQ Bot 和交易批准链接，没有必要再部署 Apprise、message-pusher 或建设动态 Provider 平台。

## 决策

- 继续以现有通知模块为基础，只增加小型内部 `Sender.Send(ctx, config, message)` 契约和静态 Provider 分派。
- V1 Provider 固定为站内、钉钉 Webhook、官方 QQ Bot 和 SMTP。企业微信在首轮稳定且出现实际需求后按同一契约增加；不支持个人微信自动化。
- 钉钉沿用现有 HTTP 实现，并参考 [blinkbean/dingtalk](https://github.com/blinkbean/dingtalk) 的签名与 ActionCard 行为；QQ 按腾讯官方 [botgo](https://github.com/tencent-connect/botgo) 的鉴权和消息契约实现精简 HTTP 客户端。
- 不引入完整 `botgo`、通用通知聚合库、动态注册、运行时插件或独立通知服务。若直接复用开源代码，必须保留适用许可证和归属说明。
- 待批准信号、订单未知或失败、保护单失败、风控暂停和全局急停使用固定关键投递规则；普通领域事件继续由工作流决定通知渠道。
- 每个领域事件和渠道最多一条逻辑投递。失败记录、重试和死信沿用现有 Outbox/投递机制；敏感配置复用现有对称加密。
- 钉钉每机器人限制 20 条/分钟；普通消息可以合并，关键消息只允许延迟重试，不得静默丢弃。QQ 部署前必须满足消息域名、ICP备案和固定出口 IP 白名单要求。
- 通知操作按钮只打开绑定用户和信号的一次性短期 CoinSphere URL。GET 和 Bot 回调不能改变状态；批准仍需登录、五分钟密码复验、未过期信号和幂等键。

## 结果

- 新渠道复用现有管理、加密、投递和工作流能力，只增加必要协议适配。
- Go App 是通知网关唯一运行位置；单实例故障时外部通知会延迟，但持久投递记录可在重启后恢复。
- Provider 数量或协议复杂度只有在静态分派出现实际维护瓶颈后才重新评估。

## 未采用方案

- Apprise/message-pusher 独立服务：增加部署、鉴权、监控和故障点。
- `nikoksr/notify` 或完整 `botgo` 依赖：接口思路可参考，但当前渠道范围不值得引入其完整依赖图。
- Bot 回调直接审批：操作链接不是授权凭据，不能绕过站内安全边界。
